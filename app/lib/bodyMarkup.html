Origin

Born from the Hook.
Built for private execution.

Uniswap v4 Hooks made market execution programmable. Eclipse extends that capability into a private execution layer: combining private orders, matching them inside a Eclipse Wave, and settling only the remaining imbalance against public liquidity.

Nothing new to learn.

Same wallet. Same pool. Eclipse adds one private step before your swap.

  • Works with the wallet you already use.

    One signature from the wallet you already use. No new seed phrase.

  • Same pool, same liquidity.

    Public swaps and Eclipse Waves trade the same Uniswap v4 pool. No liquidity split.

  • Orders wait in a Eclipse Wave.

    A short private batch. Nobody sees buy or sell, or how much, until it settles.

  • Only the leftover hits the pool.

    Buyers and sellers fill each other first. The hook checks what is left.

  • Your funds stay yours.

    Designed so a pause can stop new orders, never refunds or withdrawals.

EclipseHook

One pool. One hook.
Two ways to trade it.

Normal swaps pass straight through. A Eclipse Wave trade fills only if the hook confirms it matches the batch exactly. No match, no fill.

        Documentation · v0.1 draft
        
        
        Eclipse
        
        
        Born from the Hook. Built for private execution.
        
        
        Uniswap v4 Hooks made market execution programmable. Eclipse extends that capability into a private execution layer: combining private orders, matching them inside a Eclipse Wave, and settling only the remaining imbalance against public liquidity.
        
        
        Design draft. Nothing described here is deployed. Contracts, proofs, integrations and audits are not live. Names, parameters and code are illustrative and will change after research.
        
      
        

      
        
        
        Overview
        
        
        Eclipse lets an existing kind of market, a public Uniswap v4 pool, expose a second execution path. Traders who use it submit private orders into a short batch called a Eclipse Wave. Compatible buy and sell orders are matched with each other. Only the difference, the net imbalance, is traded against the pool.
        
        
        The rule the whole design follows:
        
        
        Do not rebuild liquidity. Make existing liquidity privately accessible.
        
        
        Eclipse is protocol infrastructure. Specter is a planned first-party application that would use it, but the protocol must not depend on Specter. Wallets, terminals, launchpads and aggregators should be able to integrate directly.
        
      
        

      
        
        
        Mental model
        
        
        Same pool, two ways in.
        

        PUBLIC MODE
trader → router → PoolManager.swap → EclipseHook (pass-through) → pool

DARK MODE
trader → private order → Eclipse Wave → match → net
       → Eclipse Executor → PoolManager.swap → EclipseHook (verify) → pool
       → settlement
        
        
        Eclipse is not a mixer, a separate AMM, a new liquidity pool, a general privacy wallet or a new proof system.
        
      
        

      
        
        
        Glossary
        
        
        
          
        Eclipse WaveA discrete batch window. Orders accumulate while it is open, lock at cutoff, then match, execute and settle together.
        
          
        CommitmentA hash that binds an order's terms without revealing them before execution.
        
          
        Internal matchBuy and sell volume inside one wave that offsets each other and never touches the pool.
        
          
        Net imbalanceWhat is left after internal matching. The only amount that trades against public liquidity.
        
          
        Eclipse ExecutorThe contract that submits a wave's net trade to the PoolManager.
        
          
        EclipseHookThe v4 hook on the pool that verifies dark executions and records their results.
        
          
        Settlement rootA commitment to every user's final output for a wave.
        
          
        Netting efficiencyInternally matched volume divided by gross private volume.
        
        
        
      
        

      
        
        
        Eclipse Wave lifecycle
        
        
        OPENLOCKEDMATCHINGPROVINGEXECUTINGSETTLINGSETTLEDFAILED
        
        
        While a wave is OPEN, orders accumulate. At cutoff the wave becomes LOCKED and no order can join or leave. Matching, proving, execution and settlement follow.
        
        
        Wave length is a trade-off. Short waves feel faster but have a smaller privacy set. Long waves gather more orders but add latency and price movement. Research targets are 15, 30, 60 and 120 seconds, with 30 to 60 seconds as a testnet starting point. The demo on this site uses 30 second waves with accelerated settlement.
        
        
        Never publish gross buy or sell imbalance, net direction or large-order presence before a wave executes. Only post-execution statistics are public.

        Matching & clearing
        
        
        Matching is deterministic. There is no operator discretion over who fills or at what price. Candidate price policies still under evaluation:
        
        
        • A · Uniswap execution price reference
        • B · midpoint from an oracle or external reference
        • C · batch clearing price
        • D · VWAP from external execution
        
        
        The demo uses an illustrative model: matched volume clears at a simulated mid, and the net side shares the pool's price impact pro-rata. Every wave must reconcile:
        

        BUY − SELL = NET        // subject to fees and price conversion
gross = matched_buy + matched_sell + net
        
      
        

      
        
        
        Partial fills & slippage
        
        
        If not all volume can execute, the default is a pro-rata fill:
        

        userFill = userRequested × totalFilled / totalRequested
        
        
        Every order carries minAmountOut or a maximum price. If the aggregate execution would violate it, that order is not filled. The wave removes it, re-nets, re-proves and executes the remaining valid orders. You can trigger this in the demo terminal by setting 0.1% slippage on a large order.
        
      
        

      
        
        
        Settlement invariants
        

        total user inputs = internal matched inputs + external execution inputs
                  + fees + refund / remainder
total outputs credited = actual outputs received
        
        
        No synthetic balance creation. Every order, wave, settlement root and proof is replay-protected: a wave settles once and an order is consumed once.
        
      
        

      
        
        
        EclipseHook
        
        
        EclipseHook is the enforcement gateway between private order flow and public Uniswap v4 liquidity. It is attached to the pool when the pool is initialized. Every swap in that pool calls it, which is what lets the pool serve two paths on one liquidity source.
        
        
        
          
        Public path
        No Eclipse data in hookData. The hook returns immediately and the swap behaves like any v4 swap.
        
          
        Eclipse path
        The Eclipse Executor passes the wave reference in hookData. beforeSwap verifies it, the pool fills it, afterSwap records the result.
        
        
        
        
        The hook does not provide privacy by itself. Privacy comes from the order layer in front of it. The hook makes the eclipse path trust-minimized and enforceable on-chain.
        
      
        

      
        
        
        beforeSwap checks
        
        
        
          
        CheckReverts with
        
          
        Caller is the registered Eclipse ExecutorNotDarkExecutor()
        
          
        Pool is registered for EclipsePoolNotRegistered()
        
          
        Wave is locked and not yet settledWaveAlreadySettled(waveId)
        
          
        Commitment root matches the locked waveRootMismatch()
        
          
        Swap amount equals the proven net imbalanceAmountMismatch(expected, got)
        
          
        Execution deadline has not passedDeadlineExpired()
        
        
        
        
        Never trust hookData blindly. Every field it carries is checked against state the hook already holds.
        
      
        

      
        
        
        afterSwap accounting
        
        
        On the eclipse path, afterSwap captures the actual swap delta, marks the wave as executed, takes the Eclipse fee and emits the data the public proof page reads.
        

        function afterSwap(..., BalanceDelta delta, bytes calldata hookData)
    external onlyPoolManager returns (bytes4, int128)
{
    if (hookData.length == 0) return (selector, 0);   // public path
    Wave storage w = waves[waveId];
    w.state  = EXECUTED;
    w.result = delta;
    int128 fee = _fee(delta, FEE_BPS);             // via afterSwapReturnDelta
    emit DarkWaveExecuted(waveId, delta, w.commitmentRoot);
    return (selector, fee);
}
        
      
        

      
        
        
        Permissions
        
        
        In v4 a hook's permissions are encoded in the low bits of its address and fixed for the pool's lifetime. Proposed set:
        
        
        
          
        FlagUsedWhy
        
          
        beforeInitializeYesOnly allow pools created through the Eclipse registry
        
          
        beforeSwapYesVerify dark executions
        
          
        afterSwapYesRecord results, emit proof data
        
          
        afterSwapReturnDeltaYesTake the Eclipse fee from output
        
          
        Liquidity and donate hooksNoLPs use the pool exactly like any v4 pool
        
        
        
      
        

      
        
        
        Errors
        
        
        A revert means the swap never happened: no balances move and the wave can be retried or failed safely.
        
        
        
          
        NotDarkExecutor()Someone other than the Eclipse Executor tried the eclipse path.
        
          
        PoolNotRegistered()The pool is not enabled for Eclipse.
        
          
        WaveAlreadySettled(waveId)Replay of an executed wave.
        
          
        RootMismatch()The commitment root differs from the locked wave.
        
          
        AmountMismatch(expected, got)The trade size differs from the proven net imbalance.
        
          
        DeadlineExpired()The execution window closed.
        
        
        
      
        

      
        
        
        Pools with another hook
        
        
        A v4 pool has exactly one hook, chosen at initialization. A pool that already runs a different hook, such as a graduated Pons pool, cannot add EclipseHook later.
        
        
        For those pools the plan is an executor-only route: the Eclipse Executor performs the same checks before calling the pool, and the pool's own hook stays untouched. No liquidity migration is required, but enforcement lives in the executor rather than at pool level. V1 supports graduated Pons tokens only, never the pre-graduation bonding curve.
        
      
        

      
        
        
        Architecture
        
        
        
          
        LayerRole
        
          
        ApplicationsSubmit orders. Specter (planned first-party app), wallets, trading terminals, launchpads and aggregators.
        
          
        EclipseCoordinates private execution: order gateway, Eclipse Wave scheduler, deterministic matcher, Eclipse Executor and settlement receipts.
        
          
        Uniswap v4 + EclipseHookPublic liquidity, price discovery and swap execution. The hook enforces the eclipse path on the pool.
        
        
        
        
        Specter is a planned first-party application for private balances and portfolios, with the line "Your portfolio shouldn't be public." When a Specter user trades, the order routes through Eclipse. The protocol is designed to work without it.

        Admin, pause & upgrades
        
        
        
          
        Admin can (2-of-3 multisig)
        • Register supported pools
        • Pause new dark orders
        • Update bounded fee parameters
        • Add a verifier version or execution adapter
        
          
        Admin cannot
        • Steal user funds
        • Change a settled wave or rewrite an order
        • Forge a valid proof
        • Redirect user output
        
        
        
        
        Pause blocks new orders and new waves. It never blocks settlement of already locked valid waves, refunds or user exit. Prefer versioned deployments (EclipseHook V1, V2…) over silent upgrades. If upgradeability is required: multisig, timelock and public notice.
        
      
        

      
        
        
        Threat model
        
        
        Each actor needs a written answer for what they know, what they can do, what they cannot do, the worst case and the mitigation.
        
        
        
          
        ActorIdeal failure mode
        
          
        MatcherCannot choose prices or favour users; cannot steal funds
        
          
        RelayerCan delay, cannot change orders, recipients or minimums
        
          
        ExecutorCannot exceed the proven net; the hook rejects it
        
          
        MEV searcherSees only post-execution aggregates
        
          
        AdminBounded powers, see above
        
          
        Chain observerSees one aggregate trade per wave, plus deposits and payouts until funding is shielded
        
        
        
        
        Open questions before mainnet: can the operator map wallet to order, can the relayer correlate IPs, can an observer infer users from timing, can a user self-submit, and can a user exit if the service disappears. These answers decide every marketing claim.
