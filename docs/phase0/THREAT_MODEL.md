# Threat Model (Phase 0 Research)

**Status:** Research draft, written for the Phase 1 (transparent, no-ZK, no encrypted orders) design. Per brief §41: "These answers determine marketing claims" — most privacy questions below are honestly **not yet mitigated** at Phase 1, and the frontend/marketing copy must not claim otherwise until the referenced later phase ships.

---

## 1. Threat actor table (brief §40)

| Actor | Knows | Can do | Cannot do | Worst case | Mitigation |
|---|---|---|---|---|---|
| **Matcher / batcher** | All order contents in cleartext at Phase 1 (no encryption yet) — amount, direction, owner | Computes the netting/matching plan | Move user funds directly (funds stay in escrow/the pool until settlement); choose an arbitrary clearing price (pinned to pool mid per `MATCHING_MODEL.md`) | Operator front-runs or leaks order flow it can see in full | Phase 1: none beyond "single trusted operator," disclosed as such. Phase 4: ZK validity proof removes the need to trust the matcher's *computation*; does not by itself hide order contents from it — that is Phase 2's job. |
| **Relayer** | The batch and proof it's asked to submit; can see submission timing and (without additional care) the submitter's IP | Delay submission; choose not to submit | Change user order, recipient, or `minAmountOut` (these are what the hook/executor check against); forge a valid proof; steal funds | Relayer censors/delays a wave | Brief §31's ideal failure mode: "can delay, cannot steal." Multiple independent relayers (Phase 3+) reduce censorship risk; not implemented at Phase 1 (single operator-run relayer only). |
| **Prover** (Phase 4+; N/A at Phase 1 — no ZK yet) | Full witness data needed to construct the proof, i.e. the same order contents the matcher sees, unless a future design separates these roles | Produce a proof, or refuse to | Reconstruct a *valid* proof for an invalid batch (soundness of the chosen proof system, see `ZK_STACK_DECISION.md`) | Prover is also the matcher and can correlate order contents it already had access to — proving doesn't add new leakage beyond what the matcher already knew | Separating "matcher" and "prover" into different operators does not hide data from a colluding pair; real mitigation is Phase 2 encryption so neither role sees cleartext order content in the first place. |
| **Eclipse Executor** | The wave's net imbalance and settlement plan it's told to submit | Submit the batch to `PoolManager.swap()` via `EclipseHook` | Submit an amount that doesn't match the proven/registered net imbalance (`AmountMismatch` revert, see `HOOK_DESIGN.md` §3); redirect output recipients | Executor is unavailable/censors → wave fails safely (`FAILED` state, brief §9), no fund loss | Hook-enforced invariants (§3 of `HOOK_DESIGN.md`) make the executor's power purely operational (can delay/fail a wave), not custodial. |
| **Admin (2-of-3 multisig)** | Protocol-level config: registered pools, fee parameters, verifier versions | Register pools, pause new orders, update bounded fee params, add verifier/adapter versions (brief §49) | Steal funds, change a settled wave, rewrite an order, forge a valid proof, redirect user output (brief §49) | A compromised 2-of-3 could pause the protocol or register a malicious pool/adapter, not drain existing settled positions | Multisig threshold, pause scope limited per brief §50 (never blocks settlement/refund/exit), versioned-not-upgradeable hook (`HOOK_DESIGN.md` §5) bounds blast radius of a compromised key. |
| **MEV searcher** | At Phase 1: nothing extra beyond any public-mempool observer — the net trade is a normal, visible swap. Pre-execution wave imbalance must never be published (brief §53) regardless of phase. | Front-run/sandwich the net trade itself, same as any public Uniswap swap | See individual order contents at any phase (that's the point of batching, even transparently at Phase 1 the *individual* orders are still visible in the Phase 1 design since there's no encryption yet — see privacy question 2 below, this is a real Phase 1 gap, not fully solved) | Searcher sandwiches the net execution the same way it could sandwich any swap of that size | Phase 1 offers **netting**, not **order-content privacy** — smaller net footprint than N individual public swaps, but the net swap itself is as MEV-exposed as any public trade until private-RPC/commit-reveal mitigations (brief §52) are evaluated at Phase 3+. |
| **RPC provider** | Submitter IP/metadata on every request routed through it, same as any dApp | Correlate request timing/IP with on-chain activity | Alter transaction contents without detection (signed) | RPC provider deanonymizes a user by IP↔order correlation | Not mitigated at Phase 1. Candidate mitigations (private RPC, brief §52) are explicitly deferred research items, not shipped. |
| **Frontend compromise** (malicious/compromised JS served to users) | Whatever the frontend can see: wallet address, order parameters as typed | Mis-display information, attempt to submit a malformed order (still constrained by on-chain checks and wallet signature review) | Forge a valid wallet signature; bypass on-chain invariants | User is tricked into signing a bad order via a convincing fake UI | Standard web-app supply-chain hygiene (brief §42: no third-party analytics receiving wallet/pair/amount/direction/order-id); wallet UIs showing raw calldata remain the backstop, same as for any dApp. |
| **Blockchain observer** (anyone reading the chain) | At Phase 1: the aggregate net trade per wave (by design — this *is* the product), plus every individual order's existence and content, since Phase 1 has no encryption yet and batching alone doesn't hide on-chain-submitted order data unless the order submission path itself is already off the public mempool | Link wallet → order (Phase 1: **yes, trivially**, since orders aren't encrypted — see privacy question 1) | Determine what a *future-phase* shielded balance holds (N/A at Phase 1, no shielded funding yet) | Full deanonymization at Phase 1 if orders are submitted on-chain in cleartext; this is why Phase 1 should route order submission through an off-chain **order gateway** (brief §44) rather than a public mempool transaction per order, even though the matching logic itself stays unencrypted | Phase 1 mitigation: private order-gateway transport (not a public tx per order) to at least avoid mempool-level correlation, even though the operator still sees cleartext. Full fix is Phase 2 (encrypted payload) + Phase 4 (ZK) together. |
| **Colluding traders** | Their own orders plus whatever side-channel information they can combine | Could attempt to signal to each other outside the protocol to game pro-rata fills or infer wave imbalance | Alter the deterministic matching/pro-rata math (`MATCHING_MODEL.md` §3) in their favor — it's formulaic, not discretionary | Colluding traders gain no formulaic advantage since fills are pro-rata and price is pool-pegged, not negotiated | Determinism itself is the mitigation (brief §14: "no operator discretion"); no additional design needed at Phase 1. |

## 2. The nine privacy questions (brief §41) — answered for Phase 1

| Question | Phase 1 answer |
|---|---|
| Can operator map wallet → order? | **Yes.** Phase 1 has no encryption; the matcher/operator sees full order contents by design (brief §20 Phase A: "Everything visible"). |
| Can matcher see amount? | **Yes**, same reason. |
| Can matcher see direction? | **Yes**, same reason. |
| Can relayer correlate IP? | **Not mitigated.** No private-RPC or IP-obfuscation work is in Phase 1 scope. |
| Can prover reconstruct order? | **N/A at Phase 1** — no prover role exists yet (no ZK until Phase 4). |
| Can execution venue (the pool/chain) identify user? | **Partially** — the net executed trade is attributed to `EclipseExecutor`'s address, not individual users' wallets, *if* order submission avoids a public per-order mempool transaction (see order-gateway note above). If orders are submitted as individual public transactions instead, this protection is lost entirely — **this is a Phase 1 design requirement, not optional**. |
| Can public observer infer a user from timing? | **Partially mitigated** by wave batching (brief §53: never publish pre-execution imbalance) but **not fully solved** — an observer who can see *order submission* timing off-chain (e.g. by compromising the order gateway) could still correlate. Full mitigation needs Phase 2 encrypted transport. |
| Can user self-submit (no reliance on a privileged party)? | **Yes, mechanically** — nothing in Phase 1 requires a user to go through Specter or any particular first-party app; any integrator can submit via the order gateway (brief §3: "Dark Mode must not depend on Specter"). This does not mean the submission path is private (see above), only that it isn't gatekept. |
| Can user exit if the service disappears? | **Yes, by design constraint** — brief §50: pause must never block settlement of already-locked valid waves, refunds, or user exit. This must be a hard Phase 1 implementation requirement and test case (brief §58: "refund path," "admin pause"), not a Phase 3+ nicety. |

## 3. Marketing-claim guardrail

Per the answers above, Phase 1 frontend/marketing copy (brief §26/§65/§75) must not claim individual-order privacy, anonymity, or MEV-proofness. The only Phase-1-honest claims are: **netting reduces public footprint and price impact versus N separate public swaps**, and **settlement is deterministic and auditable** (`/wave/[id]` public proof page). Anything about hiding *who* traded or *what they traded* waits for Phase 2 (encryption) and Phase 4 (ZK) respectively, and even then the matrix in `ROBINHOOD_POOL_MATRIX.md`/this table should be re-run per phase before updating claims — this is exactly the `/privacy` page's job per brief §36.
