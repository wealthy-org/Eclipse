## 2. Recommendation for Phase 4

**Recommended: a zkVM (SP1 or RISC Zero, Groth16-wrapped for EVM verification), not a hand-written circuit (Noir, Circom, or Halo2).**

**Why:** Eclipse's Phase 4 statement to prove is *accounting logic* (brief §18: "all orders valid, no duplication, matched amounts conserve assets, net imbalance correct, settlement outputs sum correctly") — not a cryptographic primitive. This is exactly the kind of "ordinary business logic, proven in bulk" workload zkVMs are designed for: the matching/netting code from `MATCHING_MODEL.md` can be written once in Rust and proven directly, instead of re-expressed by hand as arithmetic circuit constraints in a DSL. That dramatically reduces the risk of a translation bug between "the logic we tested" and "the logic we proved" — a bug class that circuit-based systems are especially prone to. On-chain verification cost lands in the same ~250-270k gas range as Groth16/Circom anyway (since both ultimately post a Groth16-style wrapper proof), so there is no cost penalty for the dramatically simpler development model.

**Between SP1 and RISC Zero specifically:** treat this as a Phase 4 implementation-time bake-off, not a Phase 0 decision — both are cited as production-grade in independent 2025-2026 benchmarking, and the real differentiator (prover cost at Eclipse's actual wave volume, GPU cluster pricing, SDK ergonomics for the specific netting logic) can't be evaluated without real code. Do not commit to one vendor contractually before a working Phase 1 netting implementation exists to port into a proof-of-concept circuit for both.

**Where Noir/Circom/Halo2 still matter:** if Phase 2's **order commitment / ownership proof** (brief §12, "EIP-712 intent signature plus encrypted transport before full shielded ownership") eventually needs a small, client-side, browser-provable statement (e.g. "I know the preimage of this commitment" or a Merkle-inclusion proof for Phase 5 private settlement) — that is a narrow, well-defined circuit, not general business logic, and is exactly Noir/Barretenberg's sweet spot (browser proving support, §1 above). **So the likely end-state is two proof systems for two different jobs**: a zkVM for the Phase 4 batch-validity proof, and Noir for any Phase 5 client-side ownership/commitment proof — not one stack for everything.

## 3. What Phase 1 (no-ZK) must not paint itself into a corner on

So that whichever path above is chosen in Phase 4 remains open:

1. **Keep the matching/netting logic in one isolated, pure-function module** (no I/O, no external calls) from Phase 1 onward — this is the exact code that gets ported into a zkVM guest program (or re-expressed as circuit constraints) later. If Phase 1 scatters this logic across a web service with side effects, Phase 4 has to rewrite it instead of proving it.
2. **Make every public input to the eventual proof explicit and stable now**: `poolId`, `waveId`, `commitmentRoot`, `netAmount`, `netSide`, `deadline` — these are the values `EclipseHook`'s `beforeSwap` already checks (see `HOOK_DESIGN.md` §3). Phase 4 should not need to change the hook's check list, only swap "trust the operator's computation" for "verify a proof of the operator's computation."
3. **Do not hardcode "trust the matcher" assumptions elsewhere** (e.g. in `EclipseExecutor` or off-chain indexers) that a future proof can't cleanly slot underneath — brief §30 already warns against this for solver competition, and the same caution applies to ZK.
