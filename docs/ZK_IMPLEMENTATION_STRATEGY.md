# ZK Implementation Strategy (Phase 4 design pass)

**Status:** Design only. No code in this doc has been written yet. Builds on `docs/phase0/ZK_STACK_DECISION.md`
(stack recommendation) and `zk/src/lib.rs` (the invariant-checking logic already drafted there — see
"What already exists" below for why that code is *not* a ZK proof yet).

## 1. Recommendation: SP1 (Succinct)

Per `ZK_STACK_DECISION.md`, both SP1 and RISC Zero are viable zkVMs. For this project specifically, **SP1**:

- Guest programs are plain Rust — the logic already drafted in `zk/src/lib.rs` (`verify_and_prove_batch`)
  can become the guest program body almost unchanged, just swapping its plain function signature for
  SP1's `sp1_zkvm::io::read` / `io::commit` pattern. No rewrite of the invariant logic.
- Groth16/PLONK-wrapped final proofs are small and cheap enough to verify on an EVM chain (a few hundred
  thousand gas) — matters once Phase 4b (on-chain verifier) happens.
- Larger, more active ecosystem and documentation than RISC Zero as of this research pass.

RISC Zero stays the fallback if SP1's toolchain gives trouble on this machine/CI.

## 2. What already exists vs. what a real proof needs

`zk/src/lib.rs`'s `verify_and_prove_batch` is a **plain Rust function**: given a witness (all order data,
in cleartext, as a normal argument), it checks the five invariants (no duplicate IDs, no expired orders,
no zero amounts, commitment hashes match, netting conserves value) and returns a `BatchPublicJournal`.
Nothing about this is private or proven — anyone who calls it sees every field of every order, and nothing
it returns is independently verifiable without re-running the same function on the same (now-revealed) data.

This is exactly the right **circuit logic** — the invariants are correct and match `MATCHING_MODEL.md`.
What's missing is the zkVM wrapper that turns "I ran this function" into "I can prove I ran this function
correctly, without showing you the input."

## 3. Public vs. private inputs

| Field | Visibility | Why |
|---|---|---|
| `pool_id`, `wave_id`, `timestamp` | **Public** | Needed by the verifier/hook to bind the proof to a specific wave. |
| Each order's `owner`, `side`, `amount_in`, `min_amount_out`, `secret` | **Private** (zkVM witness) | This is exactly what Phase 2/4 together are supposed to hide from everyone except the order's own owner. |
| `commitment_root` (Merkle root of per-order commitment hashes) | **Public** (proof output) | Lets anyone check a specific order was included, without seeing the others. |
| `gross_buy`, `gross_sell`, `internal_matched`, `net_amount`, `is_net_sell` | **Public** (proof output) | This is the aggregate the hook/pool actually needs to settle — brief §32/§39's public proof data. |
| `valid_order_count` | **Public** (proof output) | Sanity/stat figure for `/stats`, `/wave/[id]`. |

The guest program takes the private fields as witness input, re-derives the public outputs, and the zkVM
produces a proof that this computation was done correctly — the public outputs are trustworthy *without*
ever revealing the private witness to whoever checks the proof.

## 4. Where the prover runs (host/guest split)

- **Guest program** (`zk/` crate, SP1 target): the invariant-checking logic, compiled to a RISC-V ELF that
  SP1's toolchain can execute and prove.
- **Host/prover** (new: a small addition to `services/matcher/`, not the browser): assembles the witness
  from orders it already reads out of NeonDB/chain (same data `matchCore.ts`/`nettingCore.ts` already see),
  feeds it to the SP1 prover SDK, gets back a proof + public journal. This runs **after** netting is
  computed and **before** calling `settleMatchedPair`/`settleOrderPayout` — the proof becomes the
  justification for why that settlement plan is correct, instead of "trust the matcher operator."
- **Never in the browser.** Proving is computationally heavy; nothing about this belongs in `Terminal.tsx`.

## 5. On-chain verifier (Phase 4b — not this pass)

Once local proving works, the next increment is a `EclipseBatchVerifier.sol` contract (SP1's Solidity
verifier, generated by its tooling) that `EclipseHook.lockWave` or a successor function calls to check the
proof before accepting a wave's settlement plan — replacing today's `onlyOwner`-trusted `lockWave`/
`settleMatchedPair` calls with "trust the proof," which is the actual point of Phase 4 per brief §18.
This is deliberately **out of scope for this design pass** per your answer — flagged here only so the
interface (what the guest program's public journal must contain) is designed with this later consumer in
mind, not discovered after the fact.

## 6. Staged rollout

| Stage | Deliverable | Unlocks |
|---|---|---|
| **4a** (next concrete step) | SP1 guest program wrapping `zk/src/lib.rs`'s logic; host-side prover script in `services/matcher/` that can generate and locally verify a real proof for a real wave's order set. No chain changes. | First real, checkable claim that "a wave's netting was computed correctly" — provable, not just asserted. Still not connected to anything on-chain. |
| **4b** | Deploy `EclipseBatchVerifier.sol` to Robinhood Chain testnet; wire `EclipseHook`/registry to require a valid proof instead of `onlyOwner` trust for settlement. | The actual trust-minimization brief §18 is about — matcher can no longer silently mis-net a wave. |
| **4c** | Matcher daemon calls the real prover automatically as part of its settlement cycle (replacing the manual `npm run match`/`npm run daemon` trust-based flow). | Full automation with cryptographic guarantees, not manual + trusted. |

## 7. Honest caveat this doesn't solve by itself

Even with 4a–4c complete, the **matcher/operator still sees plaintext orders** before proving anything —
ZK here proves the *computation* was done correctly, it does not by itself hide orders from the operator
(that's Phase 2's encrypted-order-layer job, tracked separately, not re-derived here). `THREAT_MODEL.md`'s
privacy-question table should be re-answered once 4a lands, not assumed solved.
